# Compatibility with the fork (Python)

The goal is a **drop-in replacement**: commands, arguments, stdout, exit codes, the data directory, and the `credentials.json` and `messages.db` schemas and content formats all match the fork, so callers (e.g. programs that parse `已发送 msg_id=…` ("sent msg_id=…"), `OK …/EXPIRED …`, or the position at the start of history lines) need no changes.

## Module mapping

Every feature of the fork has been rewritten; new features are listed in the "New" row of the differences table below.

| Module | Original files (fork) | This repo | Verification |
|---|---|---|---|
| Protocol assets: gateway packets, persistent-connection frames, full gateway definitions, endpoint mapping | `larkx/proto/*.proto`, `lark_all_pb2.py`, `cmd_map.json` | `assets/`, `proto/proto.proto` | Rebuilt by the pipeline below; the full definitions and endpoint mapping are byte-identical to the original. `proto.proto` adds edit-version and Markdown fields on top of the original (see the differences table below) |
| Login and credentials: QR scan, cookie import, credential check | `larkx/auth.py`, `region.py` | `src/auth.ts`, `src/region.ts` | Manually tested import / check / QR initialization; credential fields match the original |
| Gateway client and persistent message connection | `larkx/client.py` | `src/client.ts` | Manually tested sending 5 message types, mark read, message links, search, history fetch, receiving echoes over the persistent connection |
| Message decoding (25 types) / request building | `larkx/proto/decoders.py`, `builders.py` | `src/proto/` | Compared item by item against parity fixtures generated by the original Python |
| Local storage (SQLite / MySQL) | `larkx/storage/` | `src/storage/` | One test suite runs against SQLite and MySQL 8.4; output when reading a Python-written store is byte-identical |
| Digital twin (trigger rules, per-chat queue, Claude Code backend) | `larkx/agent/` | `src/agent/` | Unit tests (with a fake claude command); not run end to end with real Claude |
| CLI (the fork's 14 subcommands) | `larkx/cli.py`, `main.py` | `src/cli/` | Read-only commands compared byte for byte with the original's output |
| Resource download | `larkx/media.py` | `src/media.ts` | Manually tested: downloaded images are byte-identical to the original's |
| Protocol asset regeneration pipeline | `dev/proto_pipeline/` | `scripts/proto-pipeline/` | Same inputs: all intermediate files and assets byte-identical to the original |
| Digital twin pipeline demo | `dev/demo_*.py` | `scripts/demo-agent.ts` | Prints only the prompt by default; calls the real backend only with `--live` |

## Verified byte for byte

- `lark config`, `auth status`, `auth check`, `chats`, `sessions`, `messages` (including `--json`, `--anchor`), `history` (including `--json`), `api` (including printing raw bytes as `b'...'`), `search`, `self-chat`: identical output from both versions on the same data (2026-10-13, reading a `~/.larkx` written by the Python version).
- Message content decoding (18 types + the parse-failure text), push frame parsing, all outgoing packet construction and response decoding: `tests/parity.test.ts` compares against fixtures generated by the original.
- Storage format: `content_data` matches Python's `json.dumps(ensure_ascii=False)` (separators, escaping, int64 without precision loss, float `1.0`, bytes replaced with `<n bytes>`, truncation to 20,000 characters); time columns use SQLAlchemy's `YYYY-MM-DD HH:MM:SS.ffffff`.
- Downloaded resource files, the terminal QR-code ASCII art, agent session ids (uuid5), the protocol assets and all pipeline intermediate files (except fields added to `proto.proto` later: `editVersion` / `editTimeMs` on `entities.Message`, `markdownIds` on `RichText`, and the correspondingly rebuilt `proto.binpb` and `core.binpb`).

## Intentional differences

| Aspect | Fork | This repo | Reason |
|---|---|---|---|
| Iteration order of protobuf map fields | upb hash-table slot order (stable across processes for the same set of keys, but unrelated to insertion or wire order) | Wire order | The original order carries no meaning; replicating the upb hash table would be fragile with no benefit. Effects: key order of map fields in `content_data` (JSON semantics unchanged); concatenation order of multi-part text in system message summaries; processing order of multiple messages in one push packet; wire order of map entries in outgoing packets (the server doesn't depend on it) |
| Multiple messages in one push packet | Dispatched to another event loop and processed concurrently | Processed serially in arrival order | Deterministic storage order, so callers reading by auto-increment id never see messages out of order |
| Network-layer error text | requests' exception text (e.g. `HTTPSConnectionPool(...): Read timed out.`) | `网络请求失败(<host>): <原因>` ("network request failed(<host>): <reason>") | Different runtimes make identical text impossible; the word "网络" ("network") is kept, so callers that detect network problems by matching "网络" / "timed out" still work. The text for non-2xx HTTP responses (`400 Client Error: Bad Request for url: …`) matches requests |
| Reason for gateway errors | Only requests' `400 Client Error: …` | Same text, with ` (<reason>)` appended when the gateway includes a reason in the response (`lark api` and uncaught exceptions); in the library it's in `HttpError.reason` | The reason (e.g. `chat not in thread mode`) directly tells you whether it's a parameter, permission or chat-type problem |
| Uncaught exceptions | Prints the Python stack trace, exit code 1 | Prints a single line `<ErrorType>: <message>`, exit code 1 | Callers usually take the last line as the message, so the result is the same |
| Log lines | `time \| level \| module:function:line - message` | `time \| level \| module - message` | Only the function name and line number are missing |
| Location of `.env` | python-dotenv searches upward from the package directory (the repo root for editable installs) | Current working directory (loaded automatically by Bun) | A single-file executable has no "package directory"; if needed, put a `.env` in the caller's working directory or pass environment variables directly |
| Interactive menu on expired credentials | questionary arrow-key selection (falls back to a numbered menu when unavailable) | Numbered menu | One less interactive dependency; same options and behavior |
| Login regions | `feishu`, `lark` | Adds `lark-jp` (Lark Japan data center): login domain `*.jp.larksuite.com`; gateway / persistent connection / file hosts are fixed per the messenger page's `window.__domains` to `internal-api-lark-api-jp` / `msg16-frontier-jp` / `internal-api-lark-file-jp.larksuite.com`; `Region.hosts` can override hosts derived from `domain` | The Japan data center's service hosts don't follow the `<service>.<domain>` pattern, so the original can't log in; the credentials' `region` field is written as `lark-jp`, which the original reports as an unknown region |
| Library entry point | `larkx/__init__.py` exports the client, credentials, storage and agent | Exports only what runs under both Node and Bun (credentials, client, persistent connection, resource download, logging interface) | Storage and the agent depend on Bun and aren't needed for in-process embedding (e.g. niuma); the CLI still has everything |
| Persistent-connection keepalive | websockets defaults: 10s handshake timeout; protocol-level ping every 20s, disconnect after 20s without a pong | 15s handshake timeout; application-level heartbeat every 30s, disconnect if no frame at all arrives within 65s | Node's WebSocket has no protocol-level ping; the server answers every application-level heartbeat with a frame, which shows whether the connection is still alive |
| Reconnection | Reconnects directly; messages sent while disconnected are lost | After reconnecting, backfills messages missed while disconnected (chat messages and thread replies) from chats with inbox changes, deduplicates by msg_id, stores them and passes them to the digital twin | The digital twin must not miss messages addressed to it |
| Digital twin prompt | `<message>` contains only chat, sender, time and content | When someone replies (quote or thread reply), an extra `<quote>` line carries the quoted message's sender and text; without a quote it matches the original | Seeing only a reply like "OK" or "agreed", the digital twin can't tell which message it refers to |
| Reaction events | Reaction pushes are not handled | The persistent connection decodes reaction changes (who added / removed which reaction on which message) and `listen` logs them; with `LARKX_AGENT_REACTIONS=true`, reaction changes others make on my messages go to the digital twin (`<reaction>`); `lark config` gains an `agent_reactions` entry | Lightweight confirmations, such as treating a thumbs-up as "go ahead" |
| Send failures | Fails immediately (`sendMsg` returns None) | On network errors, 5xx, or a missing message id, automatically retries twice with the same message cid (the server deduplicates by cid, so no duplicates); only then returns null / throws, with `SendUnconfirmed` carrying the cid | The digital twin's reply shouldn't be lost to a single network blip, and retries must not produce two messages |
| Markdown elements | MARKDOWN elements in rich text (tag 49, common in bot messages) are not included in the summary; `content_data` has no `markdownIds` | The summary includes their original content; `richText` in `content_data` gains `markdownIds` | For Markdown messages sent by bots, the original summary is empty and the digital twin can't see the content |
| Recall and edit | The same message re-pushed over the persistent connection is ignored as a duplicate | Messages carry `recalled` / `edited` flags (present only when true); `listen` replaces the stored content of recalled messages with `[已撤回]` ("[recalled]") (clearing `content_data`) and of edited ones with the new content; queued recalled messages are no longer passed to the digital twin, edited ones get the new content, and already-processed ones are passed again with `<edited>true</edited>` | If the other side recalls or changes a question, the digital twin must not answer the old content |
| Command permissions | None; every command can run | Before running, checks against `LARKX_ALLOW` / `LARKX_DENY` or the current account's rules in `permissions.json`; denied commands exit with 126; misconfigured rules fail with exit code 1. With no configuration, behavior matches the original. The library's `LarkClient.create` can enable the same checks with the `permissions` option (throwing `PermissionDenied`); nothing is checked when omitted | Limits what the digital twin can do, e.g. read-only, no adding members or recalling |
